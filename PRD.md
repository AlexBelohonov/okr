## 1. Purpose

A self-hosted, professional OKR workspace inspired by 7Geese. People plan measurable outcomes, align work with several strategic objectives, track prerequisites, and record progress transparently. The application is a React interface backed by a TypeScript API and PostgreSQL, deployed with Docker Compose.

PostgreSQL was explicitly selected during planning instead of SQLite or MySQL. SQLite is suitable for a single-server, low-write deployment, but PostgreSQL better supports concurrent updates and multiple isolated organizations. Database choice does not change the OKR model.

## 2. Scope and Users

The first release includes accounts, organizations, fixed roles, teams, periods, objectives, measurable key results, assignments, alignment and dependency graphs, check-ins, comments, immutable activity, notifications, administration, and outbound Slack notifications/objective updates. Performance reviews, recognition, billing, SSO, private objectives, uploads, and other external integrations are outside this release.

The working product name is OKR Workspace. The interface is English. All active members of an organization can see its objectives. One application host is the initial deployment target; production must use HTTPS.

## 3. Roles and Permissions

| Role | Permissions |
| --- | --- |
| Platform admin | Manage global account activation and organization activation. Content access still requires organization membership. |
| Organization owner | Admin rights plus ownership transfer. The last active owner cannot be removed or demoted. |
| Organization admin | Manage members, invitations, teams, periods, settings, and every organization objective. |
| Manager | Manage designated teams and their objectives; create company objectives; ordinary member rights elsewhere. |
| Member | Create personal objectives and objectives for teams they belong to. Edit objectives where assigned as lead/co-owner. |
| Viewer | Read content and manage their own follow preferences. No content editing or comments. |

Each objective requires one accountable lead owner. Co-owners have structural edit rights; contributors can check in and update metrics; followers receive notifications. Viewers cannot be assigned editing privileges. Key results can have an accountable owner. Inactive members cannot receive new assignments. Deactivation of a lead owner requires reassignment first. Historical authorship is retained.

Role explanations (R005 review follow-up): the Members page offers a keyboard-accessible, expandable guide to owner/admin/manager/member/viewer. Member and invitation role selectors show a brief description of the selected role, associated with the control for assistive technology. Invitation recipients see the same description before joining. Explanations reflect the delivered organization permissions, including designated-team manager scope and assignment-based member edits.

## 4. Requirements and Acceptance

### Accounts and Organizations

- AUTH-01: Startup flag DISABLE_SIGNUP defaults to true. Public signup is hidden, direct /signup visits redirect to sign-in, and the API rejects public account/organization registration with 403 SIGNUP_DISABLED before creating records. Set DISABLE_SIGNUP=false and recreate the API to enable public signup. The session response exposes signupEnabled so the frontend follows runtime configuration without a web rebuild. Invalid flag values fail startup. Valid single-use invitations still allow account creation bound to the invited email; login/logout and an organization switcher remain available.
- AUTH-02: Passwords are Argon2id hashes. Sessions and bearer action tokens are hashed in the database; sessions use HttpOnly, SameSite cookies with Secure enabled in production. State-changing requests require same-origin validation and a CSRF header.
- AUTH-03: Support configurable SMTP mode with verification and reset emails, and self-hosted mode with admin-issued reset links. Invitation links can be copied in both modes. Unverified emails remain visibly unverified.
- AUTH-04: Invitation expiry is seven days, reset expiry thirty minutes, verification expiry twenty-four hours, and session expiry seven days. Tokens are single-use. Password reset/change and account suspension revoke sessions.
- Account delivery detail (R003): passwords require 12-128 characters; profile edits change names, not email addresses. Invitation possession verifies the bound email; reset possession does not verify it. Reissuing a link invalidates unused links of the same action type. Existing inactive memberships are not reactivated or promoted by invitation acceptance. Copied global-account reset links currently require trusted host-operator access, not ordinary organization-admin HTTP access.
- Mail security detail (R003/R007/R009): outbox payloads temporarily hold plaintext links for delivery and are scrubbed after successful send. Protect database/backups/inbox. SMTP is at-least-once across a crash after acceptance; claims serialize concurrent workers and links remain single-use. Five failed attempts stop automatic retry. Trusted-host status and exhausted-message retry are delivered. Backup retention and queue/disk monitoring are documented operator responsibilities; no automatic token/status/audit deletion policy is installed.
- ORG-01: A person may belong to several organizations. Membership and content are isolated on every API path, database relation, and assignment.
- ORG-02: Owners/admins manage memberships, fixed roles, activation, teams, periods, and organization timezone. Membership suspension affects only that organization; platform suspension affects the whole account.
- ORG-03: Platform admin bootstrap is an explicit command, not an automatic first-user privilege grant. Last-owner protection applies to global account suspension as well as membership updates.
- Organization delivery detail (R004): organization selection is a per-account browser-tab preference; API authorization always uses the requested organization and current active membership. Owners/admins edit settings and ordinary memberships; only owners change owner roles or transfer ownership. Transfer makes the recipient an owner and the initiating owner an admin, preserving other owners. Organization, membership, and team mutations use versions; stale writes return 409 and require reload. Member search and administrative history are paginated.
- Team delivery detail (R004): active members can read the directory and teams; non-admin directory reads list only active accounts/memberships. Owners/admins create/delete teams and appoint designated managers with the manager/admin/owner role. Managers rename and manage ordinary rosters only for designated teams; they cannot appoint/remove designated managers or administer organization memberships. Membership suspension or demotion below manager/admin/owner clears designations atomically. Teams with objective references cannot be deleted.
- Offboarding detail (R004/R005/R009): suspending membership or demoting to viewer requires reassignment of every objective lead, co-owner/contributor assignment, and key-result owner reference, including archived/historical objectives. Objective detail provides lead/assignment and key-result-owner reassignment even while closed or archived; numeric values, frozen score and closing note remain unchanged. Historical authorship remains intact. Membership suspension does not revoke global account sessions or other organization access. Global suspension applies the same guards to all memberships and preserves a globally active owner in every organization, including suspended organizations. It revokes account sessions/action tokens and clears team-manager designations with team version increments. Reactivation preserves scoped membership suspension and does not restore designations or old tokens. No platform-admin privileges are inferred from signup.
- Platform delivery (R009): trusted host `platform:bootstrap` explicitly creates a verified administrator via password stdin or promotes an existing active account without changing its credentials/verification. No organization membership is granted; repeat promotion is idempotent. `/platform` and protected `/api/v1/platform` account/organization lists and activation routes work without tenant membership but never grant tenant content access. HTTP activation requires an optimistic version and reason; actor/target/before/after/reason/version audits commit atomically in global history. Platform mutations serialize account and sorted organization locks, preserving owner/offboarding invariants under concurrent tenant changes. Keep one active platform administrator; activating an organization requires a globally active owner. Host bootstrap audits attribute the target account and trusted-host source, not an authenticated OS operator identity.
- Invitation delivery detail (R004): admins issue copied invitations in both modes and optionally queue SMTP delivery. Already-present memberships must be updated explicitly rather than reinvited. Listing/status/history omit bearer tokens. Reissue invalidates earlier unused invitations; revoke closes a pending link. Invitations cannot grant owner status. Tenant admins cannot issue copied global-account reset links through HTTP; the trusted host-operator command remains available.

### Objectives and Key Results

- OKR-01: Objectives have title, description, organization, company/team/personal scope, lead, optional co-owners/contributors/followers, dates, progress mode, lifecycle, and health.
- OKR-02: Calendar-quarter periods and arbitrary inclusive start/end dates are supported. Default timezone is selected at organization creation. Cross-period alignment is allowed and differing periods remain visible.
- OKR-03: Lifecycle values are draft, active, completed, cancelled. Archive is separate and preserves history. Completion requires a closing note and freezes the score; reopening resumes live calculation. Draft/cancelled objectives do not contribute to active rollups.
- OKR-04: Key results support increase/decrease numeric metrics and binary outcomes. Numeric targets must differ from baseline. Current values may exceed targets, but normalized scores are clamped to 0-100%. Weights must be positive.
- OKR-05: Each objective scores either its key results or its direct aligned children, with equal weights by default. No scoring inputs produces 0%. Scores from both modes are never combined. A shared child contributes once to each parent; organization totals count each objective once.
- OKR-06: Structural edits and metric updates use record versions. Stale writes return a conflict and require reload. State changes and activity entries commit atomically.
- Core delivery detail (R005): owners/admins manage all objectives; leads/co-owners edit their objectives; designated managers edit their teams' objectives. Members create personal objectives with themselves as lead and team objectives for teams they belong to; managers/admins create company objectives. Contributors and optional key-result owners update current metric values, while structural metric edits require objective edit access. Active viewers can follow themselves but cannot receive editing assignments.
- Planning/explorer detail (R005): calendar quarters and custom inclusive dates are supported, including one-day periods. Objective dates must fall within a selected period. Used periods may be renamed but their dates/deletion are blocked until all references, including archived work, are moved. Planning periods have versions. Explorer filters include text, period, team, lead, lifecycle, archive, and inclusive date overlap; API also supports scope/health. My objectives includes lead, assignments, and metric ownership, with unique totals. Overview averages and overdue counts include active, unarchived objectives only; the end date is inclusive in the organization's timezone.
- Lifecycle/conflict detail (R005): objectives start draft/active. Active objectives can return to draft, complete with a required closing note, or cancel; drafts activate/cancel; closed work reopens to active. Completed/cancelled/archived work blocks structure and numeric changes until reopened/unarchived, while ownership remains reassignable. Archive replaces physical objective deletion and retains history. Key-result removal retains an audit snapshot. Metric mutations require both metric and objective versions and advance both, preventing stale completion scores. All objective/period writes hold the organization lock after the actor account lock and commit audits atomically. R006 replaces the earlier child-mode draft restriction with live weighted direct-child scoring.

### Relationships

- GRAPH-01: An objective can have multiple alignment parents, forming a directed acyclic graph. A separate graph contains prerequisites. In an alignment link, source is parent and target is child; in a dependency link, source is prerequisite and target is dependent.
- GRAPH-02: Self-links, duplicates, cross-organization links, and cycles within either graph are rejected. Graph mutations acquire an organization transaction lock so two simultaneous requests cannot create a cycle.
- GRAPH-03: Alignment changes require edit access to both endpoints. Dependency changes require edit access to the dependent and visibility of the prerequisite. An alignment link stores its weight for that parent.
- GRAPH-04: Unfinished prerequisites warn but permit work. Completion with unresolved prerequisites requires an override note. Dependencies do not change progress numerically.
- GRAPH-05: The interface offers alignment/dependency views with automatic layout, distinct edge styles, zoom, fit, selection, and a keyboard/mobile list alternative. A filtered node indicates when connected objectives are outside the current filters. Graphs read left to right: parent → child for alignment and prerequisite → dependent for dependencies. Alignment links have no arrowheads; prerequisite links retain dashed directed arrows. Connections are unlabelled; contribution weights remain visible in the connection list and editable in relationship details. Filters can be expanded/collapsed without clearing their URL-backed values. Both graph views show the lead avatar/name and scope icon, with scope represented only by an icon. Scope and team names are available through icon tooltips and accessible labels; full details retain names and dates. Clicking or keyboard-opening an objective opens a right-side details panel with updates governed by the existing API permissions, lifecycle locks and version checks.

Relationship delivery detail (R006): each graph rejects self-links, duplicates, foreign endpoints and cycles while holding the existing organization transaction lock after the actor account lock. Writes require both endpoint versions. Alignment creation/weight/removal requires live, unarchived objectives and edit rights on both; dependency creation/removal requires a live dependent editor and tenant-visible prerequisite, including closed/archived prerequisites. Dependency weights are always 1 and never affect scores. Both endpoints retain actor-attributed relationship history; audits and all version changes commit atomically.

Rollup delivery detail (R006): direct active/completed, unarchived children contribute using parent-specific weights; draft/cancelled/archived children are excluded from both numerator and denominator. An empty input set scores zero. Key results remain stored when switching modes but are used only in key-result mode. Shared children count once per parent and unique organization totals count every objective once. Scores derive from a consistent tenant graph snapshot; completed scores remain frozen until reopen. Related writes conservatively advance ancestor versions and direct dependent versions when prerequisite state can change, so stale completion/relationship forms require reload.

Prerequisite delivery detail (R006): a direct prerequisite is resolved only when completed; draft/active/cancelled prerequisites (including archived unfinished work) remain unresolved. Work and numeric updates can proceed. Completion requires a separate nonblank override note when any direct prerequisite is unresolved. The closing record and immutable audit preserve the override and prerequisite-state snapshot; reopen clears the current closing record while retaining history. Prerequisites can reopen later and become warnings again.

Graph delivery detail (R006): Alignment navigation offers separate alignment/prerequisite views, automatic Dagre layout, solid Alignment lines without arrowheads and dashed amber prerequisite arrows, zoom/fit and a right-side objective details panel. Layout flows left to right with right-side source handles and left-side target handles; graph connections omit weight/prerequisite labels because graph type and direction explain the relationship. Contribution weights retain their scoring meaning in relationship controls and list connections. A keyboard-accessible Show/Hide filters toggle collapses the filter area; new unfiltered visits start collapsed, URL-filtered visits start expanded, and a summary shows graph type/active-filter count while collapsed. Graph nodes and list entries show lead initials avatars/names and personal/company/team scope icons; compact cards use only scope icons, with the team name in the icon tooltip/accessible label. Graph cards are 253px wide and 80px tall, fitting exactly three compact rows: tinted title, lead/scope icon, then right-aligned percentage and lifecycle. Warning icons with full accessible labels/tooltips share the third row without adding height; details and the connection list retain expanded warning information. Selected cards keep the same dimensions. Cards omit planning dates/periods and use a compact owner row and one visible title line with ellipsis; the full title remains in the tooltip, accessible node name and details panel. The title has a pale teal background spanning the card width and a subtle divider. Titles do not wrap or reserve an empty second line, and spacing before owner/progress information is tight. Cards gain a subtle green body/header tint when the API-provided progress reaches 100%, including active objectives; the tint clears if progress falls below 100%. Relationship details/list connections retain cross-period/date differences. The graph canvas grows with the viewport on desktop and mobile; explanatory graph help starts collapsed behind How to read relationships. Search, period, team, lifecycle, archive and inclusive date-overlap filters survive URL reload. Visible nodes indicate unique connected objectives outside filters. All matching objectives are shown once; connected data is also available as keyboard-operable buttons in a mobile-friendly list. Nodes (Enter/Space), objective list entries and connected titles open the same panel without leaving the graph. The panel includes details, metrics, relationships, ownership, lifecycle and history, reusing full-page controls for permitted updates and conflict reload. Saved changes refresh the graph while keeping the panel open, including when an edit moves an objective outside the active filters. Escape/close returns focus to the opener or a surviving graph/list fallback. Mobile uses a full-width scrollable panel; a full-page link remains available. Removal controls have aligned, styled destructive buttons and require confirmation. Live parent editors can create an aligned child directly in the panel, including from the prerequisite view. The child form defaults to personal scope with the current member as lead and the parent’s dates/planning period; users can change these within normal creation permissions. Saving commits the new objective, assignments, parent → child alignment (default weight 1), endpoint/ancestor versions and actor audits in one API transaction. Parent version, tenant, live state, creation scope and editing rights on both objectives are rechecked; failure leaves no orphan. Fresh-child creation cannot form a cycle. The panel keeps the parent selected and offers opening the created child; cancel creates nothing. Cross-period/date differences appear in relationship details and list connections. Graph rendering loads on demand. Alignment parents have keyboard-operable Collapse/Expand children controls in the title row, plus Expand all children. Both graph types calculate positions from the complete matching graph. Collapsing/expanding only changes visibility, leaving remaining card coordinates and the current viewport/zoom unchanged. The visibility toolbar reserves a constant height so its controls do not shift the canvas. Collapsing prunes only paths from that parent; shared children remain visible through another expanded parent. A visible-count summary reports how many matching objectives remain displayed; the list alternative retains all matching objectives. Collapse preferences persist per membership/organization in browser-tab storage across refresh and data updates, and do not affect prerequisite graphs or scores. Small solid green, amber and red circles indicate on track, at risk and off track with accessible labels and tooltips. Explicit completion still requires its closing note and freezes the score; reaching 100% does not change lifecycle. Team card title colors and accents are generated consistently from team identity, stable across filters, reloads and renames. ### Collaboration and Reporting

- LOG-01: Check-ins record author, date, note, health, metric changes, and progress snapshot. Historical check-ins are immutable; corrections are new entries.
- LOG-02: Comments are timestamped. Audit events record structural edits, ownership, relationship/weight changes, lifecycle, membership, and settings. Administrative actions include actor identity. Never log credentials or tokens.
- NOTIFY-01: Assignment changes, comments, and check-ins generate in-app notifications for affected people/followers, excluding the actor. Transactional account emails use an outbox with retries.
- SLACK-01: Organization owners/admins can configure, test, pause and disconnect an incoming webhook with tenant, role, CSRF and optimistic-version checks. Store its URL with authenticated encryption bound to the organization; never return the secret or include it in audit/log/error output.
- SLACK-02: Selected objective/metric/lifecycle/relationship changes, check-ins, comments and assignment changes queue a channel message atomically with the objective audit. Check-ins qualify for either objective-update or notification selection and produce one message. Capture title, actor, progress, health, lifecycle and any note at the event time; 100% active remains Achieved and explicit completion remains required. Objective links select the correct organization and recheck membership.
- SLACK-03: The worker supports self-hosted and SMTP modes, serialized per-integration delivery, rate-limit delays, five bounded attempts and sanitized errors. Admins can inspect pending/failed/last-sent state and retry failed messages. Saving settings discards unsent messages; disconnect clears delivery records. Already-started delivery may finish during suspension/disconnection. Delivery is at-least-once and delivered content is scrubbed.
- SLACK-04: Host configuration supplies a retained 32-byte encryption key. EC2 generates it once on persistent storage, refuses invalid/missing retained keys and excludes it from Terraform inputs and release archives. Channel notifications have a separate audience from personal in-app notifications/mute preferences. The user selected outbound messages; Slack account linking, inbound commands and direct OKR editing are outside this scope.

## 5. Architecture and Data

Npm workspaces contain `apps/web`, `apps/api`, and `packages/shared`. React/Vite, React Router, TanStack Query, accessible Radix components, React Hook Form, Tailwind, Lucide, and React Flow/Dagre form the frontend. Fastify, shared Zod validation schemas, Prisma, PostgreSQL 18, and Node 24 form the backend. Dependencies are locked after installation.

Persistent entities: User, Session, AuthToken, Organization, Membership, Team, TeamMember, Period, Objective, Assignment, KeyResult, ObjectiveLink, CheckIn, Comment, Notification, AuditEvent, EmailOutbox, SlackIntegration, SlackDelivery. Tenant-scoped relationships use organization-aware foreign keys where appropriate. Indexes cover tenant/date, membership, links, activity, and token lookup.

REST API lives under `/api/v1`. Organization resources use `/orgs/:orgId/...`. The API validates inputs, enforces membership/authorization, and emits structured errors with appropriate 400/401/403/404/409 status codes. OpenAPI documentation is served at `/api/docs`. Reads never leak another organization's existence or content. The frontend and API share one origin through the web proxy.

## 6. How People Use and Manage the System

1. A trusted host explicitly bootstraps the first administrator, who signs in and creates an organization. Other people accept invitations, or use public signup when enabled. In SMTP mode verify public-signup email before creating organization content.
2. An organization owner/admin creates teams, assigns managers, invites people, and creates quarterly planning periods.
3. Managers establish company/team objectives. People create supporting objectives, select lead/co-owners/contributors, and add measurable key results.
4. Connect objectives to one or more strategic parents. Add prerequisites separately. Choose key-result or weighted-child scoring per objective.
5. Contributors post regular check-ins with metric updates and health. Owners review blockers, activity, and rollup progress.
6. At the end of the period, close objectives with an assessment note. Record a dependency override if needed. Archive completed planning work without deleting history.
7. Administrators reassign outstanding ownership before suspending users, keep at least one active owner, and review administrative audit history.

The production overlay binds web to host loopback for external TLS termination. ## 10. Delivery and Review

Each chapter delivers code or documentation, appropriate verification evidence, a revision summary, and a precise continuation point. The default review policy is to stop at chapter boundaries for user review; the user may instead choose continuous development. In either policy, an explicit pause request stops work after recording the current state, and a steering message updates the scope before more dependent work begins.

Use stable revision IDs R001, R002, and so on; review records refer to actual changes and do not imply a Git commit exists. A revision can be accepted, accepted with changes, or sent back for rework. Changes to tenant isolation, scoring semantics, authorization, authentication, or database migrations require their affected tests to be rerun.

Success for the complete application means CH01-CH10 are implemented and verified, release-blocking issues are resolved, Docker Compose startup works, and README operational commands have been exercised. Documentation approval alone does not satisfy application delivery.
